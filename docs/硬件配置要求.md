# 硬件配置要求（星易查）

本文给出星易查（桌面版 / Docker / 源码部署均适用）的**最低配置**与**推荐配置**，
重点保证扫描件 PDF OCR 与 Word 内嵌图片 OCR 能流畅运行。所有标"实测"的数字
来自 8 核 16GB 开发机上的真实语料测量，其余为按内存模型推算的工程估算。

> **一句话结论**：星易查的 OCR 走纯 CPU 推理（onnxruntime + RapidOCR），
> **不需要也不会使用显卡**；预算优先投给**内存**（决定并行提取进程数，是
> 第一硬约束），其次是 **CPU 核数**（决定多文件并行吞吐）与**单核性能**
> （决定单页 OCR 速度）。4 核 + 8GB 内存即可流畅跑日常批次。

## 一、配置速览

| 档位 | 适用场景 | CPU | 内存 | 磁盘（可用空间） | 显卡 |
|------|----------|-----|------|------------------|------|
| **最低配置** | 每批 3–5 份，单份 ≤50MB，扫描件每份 ≤100 页 | 2 核 64 位，≥2.0GHz（近十年主流 CPU） | 4GB | 5GB（机械盘可跑，建议 SSD） | 无需 |
| **推荐配置** | 每批 5–10 份，单份 ≤100MB，含数百页扫描件 | 4–8 核，≥2.4GHz | 8–16GB | 20GB SSD | 无需 |
| **大批量 / 服务器** | 每批 20–40 份，单份 ≤300MB | 16 核 | 32GB | 100GB SSD | 无需 |

三条硬性规则：

1. **必须 64 位系统**（x86_64 或 arm64）。程序本体携带 OCR/表格识别 ONNX 模型，
   32 位平台无法运行。
2. **内存不可低于 4GB**。低于 4GB 时并行提取会自动退化为单进程串行，OCR 仍能
   跑但整批耗时成倍增加；2GB 级机器（老旧本、小容器）不建议作为主力分析机。
3. **不需要独立显卡**。核显 / 无显卡均可；加显卡不产生任何加速。

## 二、OCR 的资源画像（为什么这样定）

OCR 相关负载共三类，全部在 CPU 上完成：

| 负载 | 触发条件 | 单位成本（实测） |
|------|----------|------------------|
| 扫描件 PDF 整页 OCR | PDF 页面无文字层（纯图扫描件） | 每页约 1–3 秒（视 CPU 与页面分辨率），默认**不限页数不限时长** |
| Word 内嵌图片选择性 OCR | 图片上下文出现"保证金/凭证/资质/营业执照"等证据词 | 单图约 1.5 秒（先降采样到 2400 像素长边）；内置上限：每份文件 30 张 / 90 秒，低于 10KB 的小图标直接跳过 |
| PDF 表格版面识别 | 线框检不出表格的页面 | 约 0.11–0.14 秒/页，模型常驻内存约 110MB |

两个对低配机器友好的内置设计：

- 图片 OCR 前强制降采样（标书内嵌图常见上万像素的超大图，实测同一张图
  原尺寸 28.0 秒、降到 2400 长边后 1.5 秒，且识别字数不减少），因此
  **内存和 CPU 压力已被控制在图片张数而非图片体积上**；
- Word 内嵌图有 30 张 / 90 秒 / 每份 的三重上限，一份塞了上百张图的商务标
  不会无限 OCR。

## 三、内存：第一硬约束

### 3.1 内存怎么被吃掉

一次分析的实际占用 ≈ **主进程常驻（约 0.3–0.5GB，含版面模型与 OCR 模型）+
并行提取进程数 × 单进程峰值 + 浏览器标签页（桌面版约 0.5GB）**。

其中单个提取进程的峰值内存按实测拟合为：

```
单进程峰值 ≈ 400MB + 2.2 × 批次中最大单份文件MB
```

实测锚点（auto 档、扫描文字版 PDF）：2MB 文件 → 458MB；242MB 文件 → 903MB。
大文件占内存多，是因为提取进程要持有自己的页面缓冲，并在表格通道升级时
各自加载一份约 50MB 的版面模型。

### 3.2 并行进程数自动定档（无需手工配置）

进程数 = min(批次文件数, 可用核数, 内存预算, 硬上限 16)，其中内存预算按
平台读取**可用内存**（Linux 取 MemAvailable×0.7，Windows 取可用物理内存×0.7，
macOS 无可用内存接口、按总量×0.5 刻意低估）。实测定档：

| 机器 | 242MB 大文件批次定档 |
|------|----------------------|
| 2 核 2GB 容器 | 1 进程 |
| 4 核 4GB 笔记本 | 2 进程 |
| 8 核 8GB 桌面 | 4 进程 |
| 8 核 16GB | 5 进程 |
| 16 核 32GB 服务器 | 16 进程（触顶） |
| 64 核 128GB | 16 进程（硬上限 16，多余核数帮不上提取） |

### 3.3 内存不足时的行为（不会崩，只会慢）

可用内存不够开 N 个进程时，程序自动降低并行度直至单进程串行，分析结果
完全一致，只是总耗时按比例变长。**建议系统保留 2–4GB swap / 页面文件**：
Windows 默认托管即可，别为了"性能"关掉——有 swap 时内存吃紧只是变慢，
没有 swap 则可能被系统直接杀进程，一次跑了几十分钟的分析前功尽弃。

### 3.4 按需估算

- 最低档例：5 份 50MB 标书、2 核 4GB → 2 进程 × 0.51GB + 主进程 0.4GB +
  浏览器 0.5GB ≈ **1.9GB**，4GB 机器可行但建议关闭其他大型应用。
- 推荐档例：10 份 100MB 标书、8 核 16GB → 5–6 进程 × 0.62GB + 主进程 +
  浏览器 ≈ **4.5GB**，16GB 从容；8GB 机器自动降到 4 进程左右，同样流畅。
- 服务器档例：40 份 242MB 标书、16 核 32GB → 16 进程 × 0.93GB + 主进程
  ≈ **15GB**，32GB 恰好喂饱满编进程池。

## 四、CPU：核数与单核性能各管一段

- **单核性能**决定单页 OCR 延迟（渲染 + 检测 + 识别是串行流水），这就是
  不推荐十年前老 CPU 的原因；
- **核数**决定多文件并行吞吐。实测 8 核机 4 进程并行：5 份共 4287 页的
  文字版提取 **40.3 秒 → 17.0 秒**（2.4 倍）；同批次文本相似度 2.3 秒、
  人员 + 报价提取 1.6 秒——分析阶段本身很轻，**提取（尤其 OCR）才是
  耗时主体**，这也是配置向"内存 + CPU"倾斜的原因。

时间预期参考（8 核推荐档）：

| 批次构成 | 预期总耗时 |
|----------|------------|
| 5 份文字版 PDF/docx（共 ~4000 页） | 1 分钟内 |
| 每份混有 100 页扫描件 × 5 份 | 约 5–15 分钟（OCR 主导，多份并行摊薄） |
| 单份 300+ 页纯扫描件 | 可能达数十分钟（受整体超时 3600 秒保护） |

架构支持：x86_64（Intel/AMD/海光/兆芯）与 arm64（Apple Silicon、飞腾/鲲鹏）
均可；银河麒麟 aarch64 需源码部署，见[银河麒麟部署指南](银河麒麟部署.md)。

## 五、磁盘

| 项目 | 占用 |
|------|------|
| 桌面版程序本体（安装后） | 约 0.5–0.7GB（Windows 安装包约 200MB） |
| 源码部署 venv | 约 0.5GB |
| 可选：LibreOffice（仅 `.doc` 正文提取需要） | 约 0.7GB |
| 数据目录（上传原件 + 历史记录 + 提取缓存） | 与使用量线性相关，见下 |

数据目录随批次累积：**上传文件原样保留 + 历史记录留存**（Docker 部署对应
挂载卷 `./uploads` 与 `./history`；桌面版在 `%LOCALAPPDATA%\星易查` /
`~/.local/share/星易查` / `~/Library/Application Support/星易查`）。另有
提取结果缓存（加速二次分析同一批文件），LRU 上限 200 份，通常不超过 2GB，
磁盘紧张可关（见下节）。估算公式：

```
长期可用空间 ≥ 1.5GB（程序）+ 常态留存的上传总量 × 2 + 5GB 余量
```

SSD 非硬性要求（提取是 CPU 密集型，实测 840MB 全量哈希仅 1.16 秒），但
批量上传大文件、缓存读写时 SSD 体验明显更好，推荐配置起建议 SSD。

## 六、低配机器调优（环境变量）

按"最低配置"装机或遇大扫描件时，用环境变量给 OCR 封顶（设了上限后超出
部分的扫描页跳过 OCR，界面会有提示，不影响其他维度）。所有预算参数
**0 或不设 = 不限**，与本仓库约定一致：

| 环境变量 | 作用 | 低配建议值 |
|----------|------|-----------|
| `OCR_MAX_PAGES` | 每份扫描件 PDF 最多 OCR 页数 | `50` |
| `OCR_TIME_BUDGET` | 每份文件 OCR 时长上限（秒） | `120` |
| `DOCX_IMAGE_OCR_MAX` / `DOCX_IMAGE_OCR_BUDGET` | Word 内嵌图张数 / 时长上限 | 默认 30 张 / 90 秒已够保守 |
| `EXTRACT_WORKERS` | 强制指定并行进程数（覆盖自动定档） | `1`（内存极紧张时） |
| `PDF_TABLE_LAYOUT` | `off` 可完全不加载约 50MB 表格版面模型，省约 110MB 内存与启动时间，代价是无框线表格检出率下降 | `off` |
| `EXTRACT_CACHE` | 提取结果缓存开关 | 磁盘紧张设 `0` |
| `MAX_CONTENT_LENGTH_MB` | 单次上传总量上限（超限返回 413 JSON 提示） | 按需，如 `500` |

桌面版设置环境变量的方法见各平台部署指南；Docker 部署写在
`docker-compose.yml` 的 `environment:` 段。

## 七、部署形态差异

- **桌面版（Windows/macOS/Linux）**：waitress 单进程 + 后台线程，单实例
  单用户，按上表配即可；
- **Docker / 服务器**：gunicorn 单进程 + 8 线程（gthread），**并发提交的
  多批分析会各自再起提取进程池，内存按并发批次数线性叠加**——多人共用时
  建议错峰上传，或按"并发批次数 × 单批占用"上调内存；整体分析超时
  3600 秒（gunicorn timeout 3900），不建议再调大。

## 八、自检：确认机器定档是否符合预期

1. 跑一次多文件分析，看启动日志中的 `并行提取 N 份文档（M 进程）`——
   M 就是本机实际定档；M 长期为 1 且机器核数不少，通常是可用内存不足；
2. 源码部署可执行 `./venv/bin/python3 app.py --check` 做依赖自检
   （含并行提取进程池自检，不过只告警降级、不阻断）；
3. 扫描件 OCR 期间界面会逐页显示"OCR识别"进度，若每页耗时超过 5 秒，
   说明单核性能偏弱，建议降低 `DOCX_IMAGE_OCR_MAX_SIDE`（默认 2400）
   或设置 `OCR_MAX_PAGES` 封顶。
